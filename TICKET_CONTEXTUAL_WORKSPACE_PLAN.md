# Ticket Contextual Workspace

## Context

Ticket harus menjadi unit kerja beridentitas stabil yang memindahkan koordinasi operasional dari percakapan WhatsApp yang tersebar ke satu ruang bersama. Implementasi sekarang baru menyediakan board personal, form metadata, dan perpindahan status; kartu membuka form edit, creator kehilangan akses ketika menugaskan ticket ke orang lain, dan komentar/activity yang sudah dijanjikan README belum ada. End state increment ini: semua staf aktif dapat menemukan ticket, membaca konteksnya, mengikuti percakapan dan riwayat perubahan, sementara satu assignee tetap menjadi PIC; ticket boleh masuk sebagai General lalu ditempelkan ke Event atau Job, dan ticket ber-context Job memakai PIC Job sebagai default assignee tanpa mengunci keduanya. Fokus hanya ruang koordinasi inti—due date, blocker/readiness, mention, notifikasi, dan attachment komentar tidak ditambahkan pada increment ini.

## User stories & flow

1. **Intake sebelum konteks lengkap.** Sebagai staf operasional, saya ingin membuat ticket General tanpa assignee ketika permintaan baru masuk, agar pekerjaan tidak tertinggal di WhatsApp sambil Event, Job, atau PIC belum diketahui. Hasilnya ticket muncul di antrean `Belum ditugaskan`, mempunyai nomor stabil, creator, dan activity `CREATED`.
2. **Menempelkan ticket ke Job dan `assignedTo`.** Sebagai creator atau assignee, saya ingin memilih Job sebagai context dan melihat field `Ditugaskan ke` otomatis terisi dari `job.assignedToId`, agar PIC Job tidak perlu dipilih ulang. Nilai ini hanya default: saya dapat menerima, mengganti ke user aktif lain, atau memilih `Belum ditugaskan`; setelah disimpan, `ticket.assigneeId` berdiri sendiri dan perubahan PIC Job berikutnya tidak diam-diam memindahkan ticket.
3. **Mengambil dan memindahkan tanggung jawab.** Sebagai staf aktif, saya ingin membuka ticket unassigned lalu menekan `Ambil ticket`, agar ticket masuk ke board `Ticket saya`. Sebagai assignee, saya ingin memilih `Ganti PIC` atau `Lepaskan assignment`, agar handover eksplisit; reassign memindahkan ticket ke board user tujuan, unassign mengembalikannya ke antrean bersama, dan keduanya menghasilkan `ASSIGNEE_CHANGED`.
4. **Koordinasi pada satu topik.** Sebagai creator, assignee, atau staf lain, saya ingin membuka URL detail ticket, membaca context/instruksi/current PIC, lalu menulis komentar, agar tambahan informasi, koreksi, dan keputusan tidak tersebar. Semua komentar dan perubahan lifecycle tampil kronologis dengan actor dan waktu.
5. **Menutup pekerjaan dengan hasil.** Sebagai assignee, saya ingin memindahkan ticket dari Todo ke Progress lalu Done dengan completion note, agar status dan hasil terakhir dapat dibaca tim. Jika pekerjaan dibuka kembali, alasan wajib dicatat dan timeline lama tetap utuh.

```text
Permintaan masuk
  → buat General / Event / Job ticket
  → jika Job: prefill Ditugaskan ke dari job.assignedToId
  → creator menerima default, mengganti PIC, atau memilih unassigned
  → ticket masuk Ticket saya / Belum ditugaskan / Semua ticket
  → staf berdiskusi di detail ticket; assignment dan status tercatat sebagai activity
  → assignee menyelesaikan dengan completion note atau handover lewat reassign
```

## Approach

1. **Jadikan Ticket aggregate kolaboratif dan storage-neutral.**
   - Di `domain/ticket/types.ts`, ubah `TicketContext` menjadi union tepat `{ kind: 'GENERAL' } | { kind: 'EVENT'; id: string } | { kind: 'JOB'; id: string }`; hapus `eventId`, tambahkan `creatorId: string | null` untuk kompatibilitas row lama, ubah `assigneeId` menjadi `string | null`, tambahkan `lastActivityAt`, dan pertahankan status `TODO | PROGRESS | DONE`, priority `NORMAL | URGENT`, `order`, completion note, serta timestamp yang sudah ada. `Ticket.assigneeId` tetap field PIC milik Ticket; `LocalJob.assignedToId` hanya sumber default ketika memilih Job, bukan relasi yang terus disinkronkan.
   - Tambahkan `TicketComment { id, ticketId, authorId, body, createdAt }` dan discriminated union `TicketActivity`: `CREATED`, `DETAILS_CHANGED` (daftar field `TITLE | DESCRIPTION | PRIORITY | CONTEXT` dengan nilai before/after), `ASSIGNEE_CHANGED` (assignee before/after), dan `STATUS_CHANGED` (status before/after plus completion/reopen note). Semua activity memiliki `id`, `ticketId`, `actorId: string | null`, dan `occurredAt`; `null` hanya untuk data legacy yang memang tidak mempunyai attribution.
   - Di `domain/ticket/validation.ts`, ikuti pola Zod dari `domain/event/validation.ts`: ekspor schema untuk context, create/edit input, assignment, status move, dan comment. General tidak mempunyai `id`; Event/Job wajib mempunyai `id`; judul dan comment ditrim serta tidak boleh kosong; assignee boleh `null`; pindah ke `DONE` tetap mewajibkan completion note dan keluar dari `DONE` tetap mewajibkan reopen reason.
   - Perluas `domain/ticket/validation.test.ts` hanya untuk invariant yang berisiko: General valid tanpa context ID, assignee `null` valid, Event/Job kosong ditolak, whitespace-only comment ditolak, dan aturan completion/reopen tetap berlaku. Buat `domain/ticket/timeline.ts` dengan comparator murni yang mengurutkan `createdAt/occurredAt` lalu `id`, uji tie-breaker di `domain/ticket/timeline.test.ts`, dan masukkan file test baru ke script `domain:test` di `package.json`.

2. **Migrasikan ticket dari generic JSON record menjadi model Supabase bertipe tanpa menghilangkan ticket lama.**
   - Tambahkan `supabase/migrations/20261006000000_ticket_collaboration.sql`. Extend `public.tickets` dengan typed columns: `ticket_number bigint generated by default as identity`, nullable `creator_id` dan `assignee_id` FK ke `app_users`, `context_kind`, nullable `context_id`, `title`, nullable `description`, `status`, `sort_order`, `priority`, nullable `completion_note`/`completed_at`, `updated_by_id`, `last_activity_at`, serta timestamp yang sudah ada. Backfill dari `payload`, renumber ticket legacy secara deterministik per workspace berdasarkan `created_at, id`, set identity sequence di atas nomor terbesar, map creator legacy ke assignee yang tersimpan jika user masih ada, dan biarkan creator `null` bila attribution lama tidak dapat dibuktikan. Setelah backfill dan constraints lolos, drop `payload` khusus dari `tickets`; jangan membuat compatibility read path.
   - Enforce database checks untuk `context_kind in ('GENERAL','EVENT','JOB')`, `context_id is null` hanya untuk General dan non-null untuk Event/Job, `status in ('TODO','PROGRESS','DONE')`, `priority in ('NORMAL','URGENT')`, `sort_order > 0`, judul nonblank, dan completion note/timestamp hanya serta selalu ada ketika status `DONE`. Tambahkan indexes untuk board `(workspace_id, assignee_id, status, sort_order)`, context `(workspace_id, context_kind, context_id)`, dan uniqueness `(workspace_id, ticket_number)`.
   - Buat `ticket_comments` dengan composite FK `(workspace_id, ticket_id)` `ON DELETE CASCADE`, author FK, body nonblank, dan `created_at`; buat `ticket_activities` dengan FK ticket cascade, nullable actor FK, constrained `kind`, JSONB `change`, dan `occurred_at`. Aktifkan RLS, cabut akses `anon`/`authenticated`, dan index masing-masing timeline pada `(workspace_id, ticket_id, occurred_at, id)`.
   - Pasang trigger pada insert/update `tickets` yang menulis activity dalam transaksi row yang sama: `CREATED` saat insert; satu activity per kelompok detail, assignment, dan status yang benar-benar berubah saat update, memakai `updated_by_id` sebagai actor dan before/after values sebagai JSON terstruktur. Trigger mengubah `last_activity_at` hanya untuk perubahan yang menghasilkan activity; trigger insert comment juga mengubah `last_activity_at`, sedangkan reorder-only (`sort_order`) tidak menghasilkan activity dan tidak mengubah waktu aktivitas.
   - Tambahkan server-only SQL functions `create_ticket`, `edit_ticket`, `assign_ticket`, dan `move_ticket` agar penentuan posisi serta mutasinya atomik. `create_ticket` mengalokasikan `sort_order = max + 1` pada assignee/TODO; `edit_ticket` mengubah metadata dan, bila effective assignee ikut berubah karena default Job/override, memindahkan posisi dalam update yang sama; `assign_ticket` menangani action Ambil/Ganti PIC/Lepaskan tanpa mengubah status; `move_ticket` menerima workspace, actor, ticket, target status, optional ordered ticket IDs, completion/reopen note. Function yang mengubah assignment mengunci scope assignee/status asal dan tujuan. Jika urutan move dikirim, moved ID plus seluruh ID ticket lain milik assignee pada destination column harus muncul tepat sekali; tanpa urutan ticket di-append ke destination. Trigger tetap mencatat perubahan auditable. Revoke execute keempat function dari `public`, `anon`, dan `authenticated`; hanya service-role API yang memanggilnya.

3. **Pindahkan seluruh akses ticket ke API terautentikasi dan hapus global “active user” preference.**
   - Tambahkan route handlers `app/api/tickets/route.ts` (`GET` list dengan filter `scope=mine|unassigned|all`, optional `contextKind/contextId`; `POST` create), `app/api/tickets/[ticketId]/route.ts` (`GET` detail + comments + activities; `PATCH` discriminated actions `EDIT`, `ASSIGN`, `MOVE`), dan `app/api/tickets/[ticketId]/comments/route.ts` (`POST` comment). Reuse `getEventApiContext()` untuk session email → `userId/workspaceId`, lalu pastikan actor masih aktif sebelum setiap mutation.
   - Semua `app_users` aktif pada default workspace boleh list/open/comment, edit metadata, assign/reassign/unassign, dan mengubah status. Server—bukan payload browser—menentukan creator/actor. `POST` menerima `{ title, description, context, priority, assigneeId?: string | null }`: `undefined` pada Job memakai `job.payload.assignedToId` bila user itu aktif, sedangkan explicit `null` berarti sengaja unassigned. `PATCH EDIT` menerima metadata plus optional `assigneeId`; saat context berubah ke Job dan ticket masih unassigned, `undefined` mengambil default PIC Job, tetapi assignee ticket yang sudah ada tidak pernah ditimpa otomatis. `PATCH ASSIGN` menerima `{ assigneeId: string | null }` dan meng-append posisi pada assignee/status tujuan tanpa mengubah status; `PATCH MOVE` menerima `{ status, orderedTicketIds?, completionNote?, reopenReason? }`; comment menerima `{ body }`. Tolak assignee nonaktif; untuk context baru, Event wajib ada tanpa row `event_cancellations`, sedangkan Job wajib mempunyai payload status selain `COMPLETED/CANCELLED` dan menunjuk Event yang belum dibatalkan. Ticket lama tetap dapat dibaca bila referensinya kemudian tidak aktif/hilang.
   - List GET mengembalikan `Ticket[]` termasuk `lastActivityAt`, sorted per scope/status/order; `scope=mine` selalu memakai actor session, bukan ID dari query. Detail GET mengembalikan `{ ticket, comments, activities }` dan nama user tetap di-resolve UI dari `listUsers`; referensi user/context yang hilang dirender sebagai “Tidak tersedia”, bukan menyebabkan 500. Return 404 untuk ticket yang tidak ada, 400 untuk validation/transition error, 401 untuk session kosong, dan 503 untuk kegagalan database.
   - Di `lib/data-client.ts`, ganti blok ticket lama dengan façade `listTickets(filters)`, `getTicketDetail(ticketId)`, `createTicket(input)`, `updateTicketDetails(ticketId, input)`, `assignTicket(ticketId, assigneeId)`, `moveAndReorderTickets(...)`, dan `addTicketComment(ticketId, body)` yang hanya memanggil route di atas. Hapus `activeTicketUser`, `getActiveUser`, `setActiveWorkspaceUser`, `listMyTickets`, `listTicketsForUser`, `moveTicket`, `reorderMyTickets`, `moveAndReorderMyTickets`, `StoredTicket`, `Preference`, dan generic `'tickets'` mapping; grep saat ini menunjukkan seluruh callsite ticket lama hanya berada di `components/ticket-board.tsx`.
   - Hapus `'tickets'` dari `lib/supabase/operational-records.ts` agar `/api/operational-records` tidak lagi menjadi jalur write yang melewati aturan actor/activity. Pertahankan `preferences` karena masih dipakai sebagai backing untuk counters di façade lain.

4. **Ubah board dari editor personal menjadi pintu masuk seluruh ruang koordinasi.**
   - Refactor `components/ticket-board.tsx` memakai API baru dan session user dari `app/(dashboard)/kanban/page.tsx`; hilangkan write ke preference global. Ubah heading/navigation menjadi “Tickets” dan sediakan view `Ticket saya` (default), `Belum ditugaskan`, dan `Semua ticket`, masing-masing dengan count; search mencakup nomor, judul, deskripsi, context, dan assignee, sementara filter context/priority tetap ada.
   - Form create/edit memakai Base UI `Dialog` yang sudah ada, menyediakan pilihan “General / belum ada konteks”, Event aktif, atau Job aktif dan field `Ditugaskan ke` dengan pilihan `Belum ditugaskan`. Ketika Job dipilih, prefill assignee dari `LocalJob.assignedToId` hanya bila field belum dipilih/ticket masih unassigned; tampilkan helper `Mengikuti PIC Job sebagai default` dan tetap izinkan override sebelum simpan. Create ke assignee lain tetap terlihat di `Semua ticket`, dan creator dapat membuka detailnya.
   - Jadikan isi kartu link ke `/tickets/[ticketId]`; pertahankan drag handle terpisah. Card menampilkan nomor workspace, context, assignee/unassigned, priority, dan `lastActivityAt`. Reassign dan edit metadata dilakukan dari detail, bukan menu ellipsis palsu.
   - Pertahankan DnD hanya pada view `Ticket saya`, karena order bermakna untuk satu assignee/status; unassigned/all bersifat daftar baca. Board menghitung `orderedTicketIds` dari seluruh ticket pada destination column sebelum filter search/context/priority, bukan hanya kartu visible. Ganti `window.prompt` completion/reopen dengan Base UI `Dialog` ber-textarea wajib, dan ganti `window.alert` serta banner inline dengan event toast global `vss:toast` tone success/error sehingga semua hasil mutation muncul bottom-right sesuai kontrak repository.

5. **Tambahkan halaman detail ticket sebagai percakapan yang dapat dibagikan.**
   - Buat `app/(dashboard)/tickets/[ticketId]/page.tsx` dan komponen client `components/ticket-detail.tsx`; tidak ada komponen detail/timeline ticket yang dapat dipakai ulang saat ini. Header menampilkan `#number + title`, context link ke Event/Job bila masih ada, status, priority, field `Ditugaskan ke`, creator, description, created/updated time, serta actions `Ambil ticket` untuk unassigned, `Ganti PIC`, `Lepaskan assignment`, Edit, dan status. Semua assignment action tersedia bagi staf aktif, termasuk assignee saat handover.
   - Tampilkan comments dan system activities dalam satu timeline ascending dengan comparator domain. Comment berisi avatar/initial, nama author, timestamp absolut, dan body dengan line breaks; activity memakai icon/text yang dibentuk dari structured change, actor, dan waktu. Comment/activity immutable di UI agar audit trail tidak dapat ditulis ulang.
   - Tempatkan textarea “Tulis komentar…” di bawah timeline, reject whitespace sebelum request, disable selama submit, append respons berhasil tanpa full reload, dan toast success/error. Poll detail setiap 5 detik serta saat window kembali focus; merge berdasarkan item ID dan jangan menggeser scroll bila user sedang membaca histori, tetapi auto-scroll bila sebelumnya sudah dekat bagian bawah. Pendekatan polling dipilih karena browser tidak mempunyai akses Supabase langsung/RLS dan menghindari kanal realtime baru.
   - Render empty, loading, 404, missing actor/context, dan API error states secara eksplisit. Mobile memakai satu kolom dengan composer tetap mudah dijangkau; desktop memakai metadata sidebar dan timeline utama.

6. **Permukaan ticket pada konteks Event dan Job.**
   - Buat `components/context-ticket-list.tsx` reusable untuk `TicketContext` Event/Job: load via `listTickets({ scope: 'all', contextKind, contextId })`, tampilkan count open/done serta links ticket terbaru, empty/error state, “Lihat semua” ke board terfilter, dan “Tambah ticket” dengan query `new=1&contextKind=...&contextId=...`.
   - Di `app/(dashboard)/events/[id]/page.tsx`, ganti shortcut lama `?event=...` dengan query context baru dan tambahkan section context-ticket list. Di `app/(dashboard)/jobs/[id]/page.tsx`, tambahkan action “Tambah ticket” dan section yang sama. `app/(dashboard)/kanban/page.tsx` memvalidasi query tersebut menjadi initial `TicketContext`; ID/kind invalid tidak membuka form terpilih, sedangkan link context “Lihat semua” membuka view `Semua ticket` dengan filter context aktif agar ticket milik staf lain tidak tersembunyi.
   - Update `components/layout.tsx` label navigasi dari “Ticket Saya” ke “Tickets”; pertahankan `/kanban` sebagai URL board dan redirect `/ticket` serta `/tickets` yang sudah ada, sehingga tidak ada route alias baru. Route `/tickets/[id]` tetap menjadi canonical shareable detail.

## Assumptions & contingencies

- Semua `app_users` aktif dalam workspace dipercaya sebagai kolaborator penuh untuk Ticket; assignee adalah PIC tunggal, bukan batas visibilitas/komentar. Role-based ticket privacy belum diperlukan.
- General dipakai untuk intake yang belum mempunyai Event/Job; context dapat diubah kemudian dan perubahan selalu diaudit.
- Untuk context Job, `LocalJob.assignedToId` adalah nilai awal convenience, bukan source of truth setelah Ticket disimpan. Bila Job tidak mempunyai PIC atau PIC-nya tidak aktif/hilang, default tetap `Belum ditugaskan`; jangan membuat assignment implisit ke creator.
- Comment pada increment ini text-only dan immutable. Attachment/evidence, edit/delete comment, due date, blocker/readiness, mention, dan notification memerlukan kontrak produk tersendiri dan tidak disisipkan ke implementasi ini.
- Status tetap tiga kolom `TODO`, `PROGRESS`, `DONE`; kebutuhan “waiting/blocker” tidak dipalsukan sebagai status keempat karena temuan domain menyatakannya sebagai dimensi terpisah.
- Bila row legacy menunjuk assignee/context yang sudah hilang, migration mempertahankan ticket dengan actor/assignee nullable atau context label fallback; jangan membuat user/event/job palsu dan jangan membuang row.
