## Context

Implement every CEISA 4.0 GET capability that directly supports the project’s BC 2.3, BC 2.5, BC 3.0, shipment, and `CustomsJob` workflows. CEISA business calls remain GET-only; OAuth login is the sole background POST prerequisite, using credentials entered once by an administrator in application settings. Credentials must be encrypted at rest, never returned to the browser, and all vendor responses remain provisional until validated against a live H2H environment.

## Approach

1. **Create a secure, workspace-scoped CEISA connection setting.**
   - Add a Supabase migration for one `ceisa_connections` row per workspace with `credentials_ciphertext`, `credentials_iv`, `credentials_tag`, `key_version`, `verification_state` (`UNCONFIGURED | UNVERIFIED | VERIFIED | FAILED`), `last_verified_at`, `created_at`, and `updated_at`; enable RLS and revoke `anon`/`authenticated` access so only authenticated server routes using the service role can access it.
   - Encrypt one JSON object `{ username, password, apiKey, companyId?, idPlatform? }` with AES-256-GCM from Node `crypto`. Require a base64-encoded 32-byte `CEISA_CREDENTIAL_ENCRYPTION_KEY`; keep `CEISA_BASE_URL`, `CEISA_AUTH_BASE_URL`, optional `CEISA_ORIGIN`, and `CEISA_REQUEST_TIMEOUT_MS` in server environment variables rather than the database to prevent an administrator-supplied URL from becoming SSRF input.
   - Add server-only helpers under `lib/server/ceisa/` for encryption/decryption and repository access. Decryption failures, a missing encryption key, or a missing Supabase configuration must fail closed without returning ciphertext or secret values.
   - Add admin-only `GET` and `PUT /api/ceisa/settings` plus `POST /api/ceisa/settings/test`. `GET` returns only `{ configured, verificationState, hasCompanyId, hasIdPlatform, lastVerifiedAt }`; it never returns usernames, secrets, tokens, or partial secret values. Initial `PUT` requires username, password, and API key; subsequent updates require all three again and atomically replace the encrypted blob, avoiding ambiguous blank-field preservation.
   - Extend `app/(dashboard)/settings/settings-manager.tsx` with a CEISA connection section composed from the installed `Dialog`, `FieldGroup`, `Field`, `Input`, and `Button` components. Saving and connection testing must emit the existing bottom-right `vss:toast` success/failure notifications. In demo mode without Supabase, render the connection as unavailable instead of holding credentials in process memory.
   - Add documented placeholders to `.env.example`; do not put any real credential, token, NITKU, NPWP, or H2H payload in repository files, logs, screenshots, or fixtures.

2. **Authenticate in the server layer and hide token lifecycle from users.**
   - Implement `getCeisaAccessToken(workspaceId)` against `${CEISA_AUTH_BASE_URL}/user/login`, sending the decrypted `username` and `password`; the active path comes from `docs/Export_openapi-auth_prod.json`, while the body and response parser remain provisional until an H2H capture confirms them.
   - Validate the login response with an endpoint-specific Zod schema and never use a token when the response does not match. Cache access tokens only in server memory per workspace, deduplicate concurrent login attempts, derive expiry from a confirmed `expires_in` or JWT `exp` when available, and otherwise invalidate on the first 401. For a business GET that returns 401, clear the cache, log in once, and retry that GET exactly once; do not implement `/user/update-token` until its active request/response contract is verified.
   - Send `Authorization: Bearer <token>` and `beacukai-api-key` on every CEISA business request. Send `id_platform` and `Origin` only when explicitly configured. Redact authorization headers, API keys, passwords, and response token fields from all errors and diagnostics.
   - Make the settings “Test connection” action perform login plus `GET /kurs/USD` as a read-only operational probe; login success marks authentication verified, while a successful rate response separately proves the operational gateway and security headers. Do not use the company-status endpoint as a connection probe because its acknowledgement semantics are still unverified.

3. **Implement an explicit, allowlisted server-side `CeisaClient`; never add a generic path proxy.**
   - Define server methods with validated inputs and endpoint-specific response parsers for:
     - `getStatusBySubmissionNumber(submissionNumber)` → `GET /status/{nomorAju}`;
     - `getPendingStatuses(companyId)` → `GET /status?idPerusahaan={NITKU}`;
     - `getDocumentDetail({ documentType, submissionNumber, customsOfficeCode })` → `GET /document/detail/{jenisDokumen}/{nomorAju}/{kodeKantor}`, allowing document code `23` for the project and rejecting unsupported project document types until CEISA documents them;
     - `downloadResponse(path)` → `GET /download-respon?path=...`, accepting only a relative path returned by CEISA and rejecting schemes, hosts, traversal, or arbitrary URLs;
     - `downloadBilling(billingCode)` → `GET /respon/billing?kodeBilling=...`;
     - `downloadForm({ kind, submissionNumber })` using `GET /respon/cetak-formulir/final?nomorAju=...` for final and the verified draft/form route for draft;
     - `searchForeignPorts(query)` → `GET /referensi/pelabuhan-luar-negeri/{kata}`;
     - `listDomesticPorts(customsOfficeCode)` → `GET /referensi/pelabuhan-dalam-negeri/{kodeKantor}`;
     - `listTpsWarehouses(customsOfficeCode)` → `GET /referensi/tps-gudang/{kodeKantor}`;
     - `getExchangeRate(currencyCode)` → `GET /kurs/{kodeValuta}`;
     - `getTariff({ hsCode, effectiveDate })` → `GET /tarif-hs?kodeHs=...&tanggal=YYYY-MM-DD`;
     - `getManifestBc11({ hostDocumentNumber, hostDocumentDate, customsOfficeCode, importerName })` → `GET /manifes-bc11` with the four documented query parameters.
   - Normalize successful responses into storage-agnostic types in `domain/ceisa/`: `CeisaStatusObservation`, `CeisaLocationReference`, `CeisaExchangeRateObservation`, `CeisaTariffObservation`, and `CeisaManifestEntry`. Preserve unknown additive vendor fields only in raw evidence, not domain values. An unknown or malformed response produces `CEISA_CONTRACT_MISMATCH`, makes no domain/job change, and records only sanitized field names/types for diagnosis.
   - Treat `GET /respon/pdf` and `GET /respon/cetak-formulir/draft` as disabled aliases until their active query contract is captured; the implemented response-PDF capability uses the documented `/download-respon?path=` route, and draft printing uses whichever draft/form route the live capture proves. This prevents guessing missing Swagger parameters while retaining the user-visible capability.
   - Do not implement the catalog’s CN PIBK, BC 1.4, BC 3.3 NPE, X-ray, e-catalogue, e-invoice, gate, e-monitoring, webhook-log, or BC 2.0 pungutan routes: the project’s domain and UI do not model those processes. Keep the existing INSW LARTAS source; CEISA `/tarif-hs` is an additional dated tariff observation, not a replacement for verified LARTAS data.

4. **Expose only authenticated application routes with strict validation and consistent errors.**
   - Add explicit GET route handlers below `app/api/ceisa/` for status, pending status, document detail, response/billing/form PDFs, location references, exchange rate, tariff, and BC 1.1 manifest. Require an application session for operational calls and admin access only for credential management/test.
   - Validate submission numbers as exactly 26 alphanumeric characters, HS codes as 8 digits, currency and office codes with bounded uppercase strings, dates as strict ISO dates before converting the BC 1.1 date to the CEISA-required format, and search text with a small bounded length. Encode every path/query value with `URL`/`URLSearchParams`; never concatenate an arbitrary URL.
   - Apply `AbortSignal.timeout` using `CEISA_REQUEST_TIMEOUT_MS`, set `Cache-Control: no-store` for status, documents, billing, forms, tariff, rate, and manifest, and propagate normalized application errors: 400 invalid input, 401 application login required, 403 admin-only settings, 404 CEISA data absent, 502 contract/upstream response invalid, and 503 credentials or CEISA transport unavailable.
   - For binary responses, require PDF content type or `%PDF-` signature before returning/storing them. Reuse the private attachment boundary in `lib/supabase/attachments.ts`; extend its owner/kind support for CEISA evidence without putting `Blob`/`File` into domain entities.

5. **Persist immutable CEISA evidence separately from operational entities.**
   - Add `ceisa_observations` with workspace, operation, correlation key, document type, submission number, response/status code, response name, observed timestamp, optional registration fields, optional attachment ID, SHA-256, and AES-GCM-encrypted raw payload. Index workspace + submission number + observed timestamp. Never overwrite an observation; deduplicate exact repeated payloads by workspace + operation + correlation key + SHA-256.
   - Add a repository that records status/detail/rate/tariff/manifest observations and returns normalized data. Reference search results remain ephemeral; when a port/TPS is selected, retain `{ kind, code, name, customsOfficeCode?, source: 'CEISA', fetchedAt }` in the consuming draft/job provenance rather than caching and mutating a global enum. Do not introduce a TTL until live response headers and change frequency are observed.
   - Decode Base64 PDF fields or fetch CEISA-returned relative response paths into private attachments and link their attachment IDs from the observation. If attachment storage succeeds but metadata/observation persistence fails, remove the uploaded object as compensation.

6. **Integrate status, detail, and evidence into the canonical `CustomsJob` workflow.**
   - Extend `CustomsJob` with `customsOfficeCode: string | null`; collect it on the existing new/edit CustomsJob pages because document detail, domestic ports, TPS, and manifest lookup require that context. Update every constructor and persisted payload caller in `lib/data-client.ts` in the same cutover; no compatibility alias.
   - On `app/(dashboard)/cipls/[id]/shipments/[shipmentId]/jobs/[jobId]/page.tsx`, add a CEISA section that is enabled only when `ajuNumber` exists. “Sinkronkan status” calls the status GET, shows the observed timeline and registration/release evidence, and emits a toast. It stores the immutable observation but does not silently mutate lifecycle state.
   - Add an explicit “Terapkan hasil CEISA” command that references a stored observation and maps `documentType + responseCode + evidence`: registration data suggests/applies `REGISTERED`; BC 2.3/2.5 SPPB applies `RELEASED`; BC 3.0 NPE applies `RELEASED`; reject applies `ON_HOLD` with `CEISA_REJECTED`; authentication/transport errors do not change lifecycle. The command must use `validateJobTransition`, append `statusHistory`, and refuse stale/mismatched observations.
   - From the same section, expose document detail, available response PDF, final/draft form, and billing PDF actions. Store downloaded PDFs as `CUSTOMS_JOB` attachments with distinct kinds and list them beside existing attachments. Disable an action with a precise explanation when CEISA did not provide the required response path, billing code, office code, or verified endpoint contract.
   - Add a company-status view to the shipment/customs area that calls `getPendingStatuses(companyId)`, matches rows to jobs by exact `nomorAju`, and offers per-job reconciliation; unmatched rows remain visible and never create jobs automatically. Keep this view disabled until sandbox evidence proves whether fetching “belum diambil” statuses acknowledges or consumes them.

7. **Use reference, rate, tariff, and manifest GETs at the data-entry points that need them.**
   - In `components/ceisa/bc23-draft-demo.tsx`, replace free-text entry for foreign ports, domestic ports, and TPS with searchable/selectable CEISA results while preserving manual fallback when integration is unavailable. Selecting a result writes its code—not display name—to `kodePelMuat`, `kodePelTransit`, `kodePelBongkar`, or `kodeTps`, and extends `Bc23Provenance` with `CEISA_REFERENCE`.
   - Domestic-port and TPS lookups require `kodeKantor`; keep controls disabled with an explanatory message until the office code is present. Foreign-port search must debounce and require at least two characters; empty/no-result responses render a normal empty state, not an error toast.
   - Add “Ambil kurs CEISA” for `kodeValuta`; apply the returned rate to `ndpbm` only after the operator selects it, retaining effective date, source, and fetched time in provenance. Do not silently replace a manually entered rate.
   - Add BC 1.1 manifest lookup using the available B/L/AWB number/date, office code, and importer name; present candidates and let the operator choose one to populate `nomorBc11`, `tanggalBc11`, `posBc11`, `subposBc11`, port, warehouse, and transport values. Never auto-select an ambiguous result.
   - Extend the existing tariff/LARTAS surface so `/tarif-hs` results appear as a separate CEISA dated tariff observation next to the existing INSW result. Preserve the existing warning that INSW verification governs LARTAS; a CEISA tariff response must not assert that LARTAS is absent.

8. **Capture and lock down live contracts without leaking production data.**
   - During the first admin connection test, permit a diagnostic mode that records HTTP status, content type, top-level field names/types, and timestamp only. Use it to finalize the provisional login/status/location/PDF parsers; never store values, identity data, tokens, API keys, or commercial payloads in repository fixtures.
   - Keep deterministic fixtures synthetic and shaped only after the live field structure is confirmed. Add regression tests for each normalizer’s success, empty response, vendor error, malformed response, and additive unknown fields; a changed vendor shape must fail closed rather than update a job incorrectly.
   - Update `docs/ceisa-integration-contract.md` with the confirmed auth body/response field names, active draft/form route, each observed response shape, and verification date. Leave each untested endpoint marked provisional rather than presenting mock-only success as live proof.

## Assumptions & contingencies

- Supabase is required for CEISA credentials and evidence. If it is not configured, CEISA settings and operational actions remain disabled; there is no demo-memory fallback for secrets.
- The active authentication base/path is `https://apis-gw.beacukai.go.id/v1/openapi-auth/user/login`, but its body/response contract is unverified. Start with the historical `{ username, password }` JSON body only as a provisional parser; activation succeeds only if a live response validates. If the live contract differs, capture field names/types, update the Zod schema and request encoding, and keep the connection `UNVERIFIED` until that exact contract passes.
- `id_platform`, `Origin`, token TTL, and refresh behavior remain optional/unverified. Send optional headers only when configured; re-login once after 401 instead of assuming the historical five-minute TTL or using `/user/update-token`.
- Several GET response schemas and the draft-form route are incomplete in Swagger. Until live H2H evidence confirms them, their UI actions stay disabled with “Kontrak CEISA belum diverifikasi”; transport/parsing failures never fall back to guessed fields or raw vendor payloads.
- If real H2H credentials or safe sample identifiers are unavailable during implementation, complete verification with the deterministic mock server and ship the connection as `UNVERIFIED`; the first live admin test must not mark individual endpoint contracts verified until each endpoint is exercised successfully.
